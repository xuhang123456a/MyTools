# 🎮 Unity C# 项目工程规范与实战经验库 (Unity Engineering Guidelines)

> 本文件汇集了 Unity 游戏开发领域的核心架构设计、热更安全与代码准则。仅在 Unity C# 项目中生效。

---

## 一、 快速失败原则与防御性代码边界 (Fail-Fast in Unity)

### 1. 严禁无意义的防御性判空
- 对于 Unity 运行所必需的核心依赖（如预制件绑定的核心组件、已初始化的状态机/数据对象、核心 UI 节点等），直接使用该依赖。引用缺失或生命周期被破坏时，让 Unity 自然产生的 `NullReferenceException` / `MissingReferenceException` 暴露真实调用栈。
- **严禁**为核心依赖添加 `if (obj == null) return`、层层嵌套判空，或仅为了判空而手工 `throw`。这些代码会增加噪音、改变原始报错位置，反而不利于定位真实问题。

### 2. 合理判空的边界
- 仅在业务逻辑上确实存在“合法/预期内的空状态”时编写判空处理：
  - 弱引用或外部对象生命周期（如动态销毁的 GameObject、异步任务取消后的回调）；
  - 可选的插件插槽、可选配置项或扩展数据。
- 对异步生命周期应优先检查任务所有权或 `CancellationToken`；不要用核心节点判空代替正确的取消流程。

## 二、 代码审查与架构指导原则 (Architecture-First)

### 1. 宏观架构设计视角
在重构或新增 Unity 逻辑时，始终从以下维度考量：
- **单一职责 (SRP)**：每个 MonoBehaviour / 类只负责单一维度的状态或行为变更，表现层与数据层严格解耦。
- **解耦与复用**：尽量避免直接硬编码跨模块单例调用，合理运用组合、观察者模式 (Events/Signals)、状态机 (FSM) 等设计模式。
- **生命周期管理**：严格掌控对象的创建、激活、重置与销毁，避免内存泄漏、闭包 GC 逃逸与野事件监听。
- **知其所以然 (Design Rationale)**：不仅给出修改代码，更要清晰讲透背后的设计考量、性能代价（CPU/GC/DrawCall）与扩展性收益。
- **代码风格简洁干练**：深度贴合项目既有规范，拒绝过度抽象与冗余胶水代码。

## 三、 Unity 代码修改与热更安全规范 (Hot-Update & HybridCLR Safety)

### 1. 程序集归属判定与热更影响评估
- **AOT vs 热更程序集划分**：
  - 检查修改的脚本属于 **AOT 母包程序集**（如主工程、基础底层 SDK、AOT 适配层）还是**热更程序集**（如 `HotUpdate.asmdef`、`Modules.asmdef`）。
  - 若修改涉及 AOT 程序集，必须明确评估并主动告知用户：**此修改需要重新打母包并提审，无法通过纯热更生效**。
- **热更边界隔离**：
  - 将稳定的 Unity 引擎适配层留在 AOT 程序集；
  - 将易变、迭代频繁的玩法与业务逻辑收敛在热更程序集中，通过接口或抽象契约与 AOT 层交互。

### 2. AOT 泛型与元数据补全
- **避免运行时 AOT 泛型实例化异常**：
  - 检查热更代码中是否引入了未在 AOT 母包中实例化的复杂泛型类型/值类型泛型方法（如 `MyStruct<T>`, `Dictionary<Enum, CustomStruct>`）。
  - 确保必要的泛型元数据已在 HybridCLR 的 AOT 补充元数据列表中声明并加载（`LoadMetadataForAOTAssembly`），确保 HybridCLR 运行时平滑执行。

### 3. 主动告知与风险披露机制
- 每次完成代码调整或重构后，必须主动向用户分析热更兼容性，指出潜在的上线风险项。

## 四、 Unity Editor 校验职责边界

- **Assets Refresh 与 Unity Editor 编译由用户执行。** Codex 不得使用 Windows/GUI 自动化控制 Unity、触发 Assets Refresh、清空或读取 Console，也不得为此消耗额外 Token。
- Codex 只执行适合命令行的窄范围源码校验，并准确说明校验范围；涉及生命周期、Prefab、Scene、序列化绑定或完整 Editor 编译时，明确标记为等待用户在 Unity 中验证。

---

## 五、 交互架构与异步生命周期设计准则 (Interaction Architecture & Async Lifecycle)

### 1. 视图自治与黑盒原则 (View Autonomy & Encapsulation)
- **拒绝穿透实现细节**：业务调度层（Bootstrap / Controller / Presenter）严禁侵入 View 内部直接操作子节点显隐或手动打断内部补间。
- **高内聚生命周期契约**：View 必须向外提供高内聚的状态重置接口（如 `HideImmediately()` / `ResetVisuals()`），所有内部动效、节点状态与渲染资源的生命周期由 View 自行管理并保证自闭环清理。

### 2. 交互链与资源释放分相原则 (Two-Phase Teardown & Event Continuity)
- **表现接管与实例销毁解耦**：当底层输入接管上层状态时，必须严格区分“表现层静默/隐藏”与“对象层销毁/释放”两个阶段。
- **保护活跃事件派发链**：严禁在输入事件派发中途（如 PointerDown）执行破坏性销毁或失活参与事件分发的容器，确保输入事件链条完整，杜绝手势被瞬间中断。

### 3. 上下文感知释放与状态机自愈闭环 (Contextual Teardown & Edge-Case Self-Healing)
- **异步退出上下文分流**：异步任务取消与退出时，资源清理行为必须根据状态机当前运行上下文进行差异化分流（如处于交互中仅静默视效，非交互状态则彻底回收）。
- **物理状态与逻辑状态双重校准**：结合底层物理输入（如真实触控点状态）对逻辑交互状态进行实时校验与自愈，确保在系统级事件丢失（如系统弹窗、屏幕越界）时状态机仍能自动闭环，杜绝僵死状态。
